SMS Pro · Construction module

Getting it running

From a fresh clone to clicking through a live project with money held in escrow. Roughly fifteen minutes, most of it waiting for npm install.

Check which database you are pointed at before you start.

Several commands below write data. The seed and test scripts are for a local or staging database — never production.

Set it up

Once per machine. Skip to the next part if you have done this already.

  1. Install dependencies

    Two separate installs — the backend and the frontend are independent packages.

    # from the repo root
cd Backend  && npm install
cd ../Frontend && npm install

    Node 20 or newer. The project is developed on Node 24.

  2. Point the backend at your database

    Backend/.env holds everything the server needs. These are the ones that matter for construction:

    KeyWhat it does
    MONGODB_URIRequired. Atlas or a local replica set — transactions need one
    PORTBackend port. Currently 5001
    USE_DEFAULT_OTPtrue makes every OTP 1234. Essential for testing
    JWT_ACCESS_EXPIRESMust be a valid timespan like 7d. A typo here breaks every login on the platform
    CLOUDINARY_*File and photo uploads
    PEXELS_API_KEYOnly for fetching catalogue photos
    REDIS_URLOptional. Without it the server skips background queues and still runs

    MongoDB must be a replica set. Every escrow movement runs inside a transaction, and a standalone server cannot do transactions. Atlas gives you this by default.

  3. Point the frontend at the backend

    In Frontend/.env, set the API base URL to a relative path so the dev proxy handles it: 

    VITE_API_BASE_URL=/api/v1

    Worth checking before you start.

    The backend runs on 5001 and the Vite dev proxy forwards /api/v1 there. But if VITE_API_BASE_URL is set to an absolute http://localhost:5000/... it bypasses the proxy entirely and calls a port with nothing on it. Every request then fails with no useful error.

    Relative is also the right value in production, where the API is served from the same origin.

Prepare the database

Each command is safe to run twice. Run them in this order — later phases depend on indexes created by earlier ones.

  1. Build the indexes

    The connection sets autoIndex: false, so nothing is created automatically. Some of these are correctness guarantees, not speed — the unique index on the escrow ledger is what makes a retried payment pay once instead of twice. 

    cd Backend
npm run migrate:escrow-indexes
npm run migrate:construction-catalogue
npm run migrate:construction-contractors
npm run migrate:construction-pipeline
npm run migrate:construction-projects
npm run migrate:construction-transparency
    expectEach ends with a line confirming the unique indexes it needed were created.

  2. Repair the older indexes

    Fifteen unique indexes across bike-rent, service-provider, quick-commerce and food were never actually built — MongoDB rejects $ne inside a partial index and silently discards the whole specification. Check first, then build. 

    npm run check:partial-indexes   # read-only
npm run repair:partial-indexes  # builds them

    If the repair reports duplicates, fix those rows by hand first. It refuses rather than choosing which duplicate survives — that is not a decision a script should make.

  3. Fill the catalogue

    Categories and services, then photographs for them.

    npm run db:seed-construction

# photos — needs PEXELS_API_KEY
node scripts/fetch-catalogue-images.js --dry-run --provider=pexels
node scripts/fetch-catalogue-images.js --provider=pexels

    Images are downloaded and re-uploaded to your own Cloudinary, so the app never depends on someone else's server staying up.

  4. Seed a working demo

    This is the one that makes every screen worth looking at: a customer, three contractors, a live project mid-build and a finished one. 

    npm run demo:construction
    expectA summary with login numbers, the current money position, and a list of URLs to visit.

    Re-running is safe — it clears only what it created. To remove it: npm run demo:construction-clean

  5. Turn the module on

    The flag lives on the shared settings document. An absent value counts as enabled, so set it deliberately rather than relying on that: 

    db.globalsettings.updateOne({}, { $set: { "modules.construction": true } })

    Or use the module switcher in the admin panel. The value is cached for ten seconds.

Run it

Two terminals, left open.

Terminal 1 · API
cd Backend
npm run dev

# http://localhost:5001
Terminal 2 · Web
cd Frontend
npm run dev

# http://localhost:5173

Background jobs are optional. With REDIS_URL set you can also run npm run worker:all. Without it the server logs that queues are skipped and carries on — the construction module's own scheduled jobs use node-cron inside the API process, so delay alerts, retention release and nightly reconciliation run either way.

Prove it still works

350 automated checks. The first three only read and are safe anywhere; the rest create records and delete them. 

# read-only — safe on any environment
npm run verify:escrow
npm run verify:construction-projects
npm run verify:construction-transparency

# create and remove data — staging only
npm run test:construction-all

# or one at a time
node scripts/verify-escrow-holds.js            #  43
node scripts/verify-contractor-onboarding.js   #  25
node scripts/verify-construction-pipeline.js   #  52
npm run test:construction-escrow               #  55
npm run test:construction-transparency         #  75
npm run test:construction-admin                #  49
npm run test:construction-acceptance           #  51
expectEvery run ends with PASSED: n   FAILED: 0.

Two static checks worth putting in CI — both catch bugs that otherwise run silently:

cd Backend  && npm run check:populate-imports
cd Frontend && npm run check:api-clients

When something is wrong

Every API call fails and the network tab shows a refused connection
Port mismatch. The backend is on 5001; check that VITE_API_BASE_URL is /api/v1 and not an absolute URL pointing somewhere else. Restart the Vite dev server after changing .env — it only reads it at startup.
Every login fails, on every module
Check JWT_ACCESS_EXPIRES. It has to be a valid timespan such as 7d or 15m. Anything else makes token signing throw, and it takes down sign-in platform-wide, not just construction.
Funding or approving a stage throws a transaction error
MongoDB is not running as a replica set. Every escrow movement is transactional. Use Atlas, or start a local single-node replica set.
The construction tab is missing for customers
The module flag is off, or the ten-second cache has not expired yet. Check modules.construction on the global settings document.
A contractor cannot be approved
Every document has to be verified first, and none may be expired. The detail screen lists exactly what is blocking it. That gate exists so nobody approves a contractor whose licence was never actually read.
Screens are empty after seeding
Run npm run db:seed-construction before npm run demo:construction — the demo builds on the catalogue and stops with a clear message if it is missing.
Money does not look right
npm run verify:construction-projects reconciles every project against the escrow ledger and reports drift without repairing it. Drifting money is something a person should look at, not something a script should quietly correct.
